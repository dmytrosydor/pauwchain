# Стратегія розвитку: від прототипу до сильної роботи і портфоліо

Стан на 27.10.2026. Документ зводить чотири аналізи: огляд літератури 2023–2026, критичне рецензування
коду й експериментів, вибір архітектури й технологій і стратегію тестування. Кожен розділ закінчується
рішенням. Номери джерел з arXiv треба ще раз звірити перед цитуванням.

## 1. Коротко

1. **Каркас добрий, але таблиці ще не є науковим результатом.** Матриця E2 дає лише 0 або 1, бо сила атак не варіюється,
   а поріг α = 0,3 виставлено навмання. Перший пріоритет — переробити експерименти, а не додавати функції.
2. **E1 уже показав, яким має бути поріг.** Чесний вузол на іншому пристрої відхиляється максимум на 0,8 % (k = 20)
   чи 3,9 % (k = 50) від розміру оновлення. Атака 5c з α = 0,3 зсуває кожен перехід на 27 %. Тобто калібрований поріг
   ловить 5c у тій версії, що є зараз. Справжнє питання: наскільки шкодить 5c, яка знає калібрований поріг.
3. **Новизну треба переформулювати** з огляду на свіжу роботу OVIG (вересень 2026), яка робить майже наш B
   з калібруванням на різному залізі. Наш внесок — єдиний стенд для кількох механізмів, атака, що
   експлуатує толерантність, і захист від неї (тест напрямку залишків), плюс економіка.
4. **Платформа для портфоліо реальна і корисна для захисту**, але будується після наукового ядра:
   RPC і потік подій у вузлі → TUI `pouwtop` → арена атак → testnet → мовна модель.

## 2. Позиціонування і новизна

| Робота | Що робить | Чим ми відрізняємось |
|---|---|---|
| Proof of Learning (Jia et al., 2021) і атаки на нього (Zhang 2022, Fang 2023) | перерахунок точок, підробка траєкторій | ми порівнюємо PoL-перевірку з іншими механізмами на одному стенді |
| OVIG (arXiv 2606.21045, 2026) | межа на різницю градієнтів, калібрована на різному залізі; 0 % успіху атак, ~14 % витрат | у нас кілька механізмів і явна атака на толерантність; потрібно прочитати повністю і зіставити |
| Gensyn OPEN-1B (arXiv 2609.17380, 2026), RepOps, RepDL (arXiv 2510.09180) | побітова відтворюваність, тобто B з δ = 0 | показуємо, чим платимо за δ > 0 і що дає δ = 0 (базова лінія B-exact) |
| SENTINEL / Pluralis (arXiv 2603.03592) | статистичні пороги в pipeline-навчанні, адаптивний атакувальник | беремо методологію: FPR < 1 %, затримка виявлення |
| Templar (Covenant-72B, arXiv 2603.08163), Prime Intellect, Bittensor | індустрійні системи | оновлюємо порівняльну таблицю в розділі 1 |
| Luu et al. CCS 2015; Zhao et al. «It Takes Two» (arXiv 2406.01794) | дилема верифікатора | рахуємо мінімальну ставку для кожного механізму з виміряних даних |

**Сформульована новизна (для вступу):**
1. Єдиний відтворюваний стенд, на якому чотири–п'ять механізмів перевірки навчання порівнюються проти
   одного набору атак за TPR при FPR = 1 %, AUC і вартістю перевірки.
2. Кількісний аналіз атаки на толерантність порогу: шкода моделі як функція порогу α і довжини переходу k.
3. Захист від неї — статистичний тест напрямку залишків перерахунку (власна пропозиція; у літературі
   найближче — EMA-детектор SENTINEL).
4. Економічна інтерпретація: яка ставка робить обман невигідним за кожного механізму.

## 4. Нові внески, які варто додати (за цінністю)

| # | Що | Навіщо | Год |
|---|---|---|---|
| 1 | **Атака «один стрибок»**: m−1 чесних переходів і один довільний (до отруєної або бекдор-моделі) | найсильніша атака на B; ймовірність пропуску (1 − q/m)^V ≈ 0,51 при q = 2, m = 10, V = 3; показує, що q треба вибирати від m | 3 |
| 2 | **Тест напрямку залишків** проти атаки на толерантність | у чесного вузла залишки перерахунку — шум, у атакувальника співнапрямлені: ‖Σr‖ росте як m, а не √m; власний захист | 6 |
| 3 | **Адаптивний атакувальник**, що знає q, α, τ і обходить A, B, D разом | вимога сучасної методології (Tramèr et al. 2020) | 5 |
| 4 | **Економіка обману** | мінімальна ставка S* = виграш·(1−p)/p; ефект дилеми верифікатора p_eff = 1 − (1−p)^(V(1−s)); таблиця «механізм → ставка» | 3 |
| 5 | **B-exact** як базова лінія (δ = 0) | на одному пристрої FRR = 0, між пристроями FRR = 100 % — мотивація для RepOps / OPEN-1B | 2 |
| 6 | **Механізм E — бісекція** в стилі Verde | дві репліки, при розбіжності бінарний пошук першого розбіжного переходу; ≈ log₂m порівнянь замість повної реплікації | 8 |
| 7 | **Нові осі E1**: потоки CPU, мікробатчі, float64, T4 на Kaggle | реальне «інше залізо» для FRR | 3 |
| 8 | **E6**: Fashion-MNIST | перевірка, що висновки не прив'язані до MNIST | 2 |

## 5. Методологія звітування

- Головне число для кожного механізму й атаки — **TPR при FPR = 1 %** (Carlini et al. 2022) плюс AUC.
- Частки виявлення і FRR — з **інтервалами Вільсона**; витрати — з бутстреп-інтервалами.
- **Pareto-графік** «виявлення проти вартості перевірки» окремо для кожної атаки.
- Вартість — у кроках навчання, FLOPs і байтах (сховище контрольних точок), не лише в секундах.
- Для E3 — **затримка виявлення в блоках** і **шкода моделі** (точність, частка цільового класу).
- Кожен прогін пише `manifest.json`: git-хеш, версії, пристрій, seed, хеш конфігу.

## 7. Платформа для портфоліо

### Рішення щодо технологій

| Питання | Вибір | Чому не інше |
|---|---|---|
| Мова вузла | **лишаємо C++20** | тема вимагає C++, автор впевнено пише на C++; переписування на Rust/Go подвоює ризик і не дає нічого дипломові |
| API вузла | **HTTP/JSON + SSE (cpp-httplib)** | один заголовок; події йдуть в один бік, команди — POST; працює з `curl -N` і браузером. gRPC тягне protobuf і кодогенерацію в обох мовах, у JSON-RPC немає стандартного стрімінгу |
| TUI `pouwtop` | **Python Textual** | мова вже є в стеку; готові таблиці й sparkline; `textual serve` відкриває той самий TUI в браузері. Rust ratatui красивіший, але додає третю мову |
| Вузол ↔ воркер | **постійний воркер через Unix socket** з тим самим кадруванням | старт Python і torch ~1–3 с на виклик, це порядок самого раунду; subprocess лишаємо прапорцем для відтворюваності |
| P2P | **лишаємо свій TCP** + підписи Ed25519 (libsodium) + inv/getdata | cpp-libp2p тягне Boost і погано підтримується; для 3–10 вузлів libp2p нічого не дає |
| Сховище | **SQLite** для ланцюга, вердиктів і метрик; ваги — файли за хешем | потрібні запити для експлорера й табло; RocksDB — лише key-value і важка збірка |
| Веб | спершу `textual serve`; далі Svelte 5 + uPlot як статика з того самого сервера | React завеликий для такої задачі |
| Testnet | один образ, `docker compose` на 5 вузлів + нативний MPS-вузол | Docker на Mac не бачить GPU, тож отримуємо «різне залізо» природно |
| Друге завдання | char-level GPT ~0,8 М параметрів | найнаочніше: текст покращується з кожним блоком. Увага вручну без SDPA, без dropout; Adam вимагає класти стан оптимізатора в точки |
| SDK | **не робимо** | досить команди `pouw task submit`; повноцінна подача завдань — окремий диплом |

## 10. Перші результати E1 (k = 20 і 50, CPU ↔ MPS)

| | k = 20 | k = 50 |
|---|---|---|
| максимальна відносна похибка чесного вузла на MPS | 0,0084 | 0,039 |
| FRR при α = 0,01 / 0,02 / 0,05 (MPS) | 0 / 0 / 0 | 0,20 / 0,10 / 0 |
| відносне відхилення атаки 5c (α_атак = 0,3, β = 0,9) | 0,27 | 0,27 |
| D: FRR при τ = 0,1 / 0,2 / 0,3 (MPS) | 0,01 / 0,06 / 0,22 | 0,025 / 0,20 / 0,83 |

Висновки: для k = 20 поріг α ≈ 0,02–0,05 дає FRR = 0 на CPU↔MPS і в 6–15 разів звужує вікно для 5c порівняно
з α = 0,3. Для k = 50 запас помітно менший. D не відрізняє 5a, 5c і плагіат від чесного вузла за низького FRR.
Повторити на T4 і з більшою кількістю стартових точок.
